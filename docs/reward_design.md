# 奖励函数设计详解

本文档详细说明 RLRefine GRPO 训练中奖励函数的设计思路、评分机制、Reward Hacking 分析及改进方向。

对应代码：[`rl/reward_builder.py`](../rl/reward_builder.py)

---

## 1. 设计目标与约束

### 1.1 核心目标

训练一个模型，使其能够：
1. **准确提取关键词**——关键词来自原文、不遗漏、不编造
2. **结构化输出**——严格遵循 JSON Schema，字段类型正确
3. **可解释推理**——提取前先进行系统性思考，展示推理链条

### 1.2 设计约束

- 奖励值归一化到 `[0, 1]` 区间
- 必须能在没有 Ground Truth 的情况下提供部分信号（无监督维度）
- 惩罚必须有上限，避免单一错误导致奖励崩溃
- 各维度权重之和为 1.0，便于消融实验

---

## 2. 五维度权重设计

```
总奖励 = F1分数 × 0.5 + Schema验证 × 0.2 + 格式分 × 0.2 + 思考质量 × 0.1 - 幻觉惩罚
```

| 维度 | 权重 | 设计理由 |
|------|------|----------|
| **准确率（F1）** | 50% | 最终交付物是关键词列表，提取质量是唯一不可妥协的目标 |
| **Schema 验证** | 20% | 确保输出可被下游系统解析：required 字段存在、类型正确、数组项格式合规 |
| **格式检查** | 20% | 确保 JSON 可解析且非空——这是 Schema 验证的前提条件 |
| **思考质量** | 10% | 鼓励模型输出推理过程以提升可解释性，但不宜权重过高，避免模型为写长文而牺牲提取精度 |
| **幻觉惩罚** | -0.1/词 | 独立于正向奖励之外的扣分机制，惩罚编造不在原文中的关键词 |

### 为什么 F1 占 50%？

F1 直接衡量"提取了什么"的质量，是面向终端用户的核心指标。如果格式完美但提取的关键词全错，输出毫无价值。将 F1 设为最大权重确保模型优化方向始终对齐业务目标。

### 为什么思考质量仅占 10%？

早期实验中，将思考权重设为 20% 会导致模型过度投入推理文本的长度和格式，而实际提取效果反而下降。10% 足以鼓励输出推理过程（相比完全不给权重），但不至于让模型为"凑字数"而偏离核心任务。

### 为什么格式和 Schema 各占 20%？

这两个维度是"基础设施"——如果 JSON 无法解析（格式失败），Schema 验证和 F1 计算都无从谈起。20% 的权重保证模型有足够动力维持输出格式的稳定性，但不会因为格式完美就拿到过高总分。

---

## 3. 各维度评分细则

### 3.1 格式检查（`_evaluate_format`，权重 0.2）

```
格式分 = 0.2 × (JSON可解析 ? 0.75 : 0) + 0.2 × (数据非空 ? 0.25 : 0)
```

- JSON 成功解析：得 75% 的格式分（0.15）
- 解析后数据非空：追加 25% 的格式分（0.05）
- 完全无法解析：0 分

设计意图：区分"格式全错"和"格式对但为空对象"两种失败模式。

### 3.2 思考质量（`_evaluate_thinking`，权重 0.1）

```
思考分 = 0.1 × (有思考标签 ? 0.5 : 0)
       + 0.1 × (长度在[50,800]字符 ? 0.3 : 0)
       + 0.1 × (含分析关键词 ? 0.2 : 0)
```

评判规则：
- 是否包含思考标签（`<think>...</think>` 或纯文本"思考"段落）：50% 子权重
- 思考内容长度是否在合理范围 [50, 800] 字符：30% 子权重
- 是否包含分析性词汇（如"分析""提取""识别""关键词""原文"）：20% 子权重

长度范围 `[50, 800]` 的含义：
- 下限 50：防止空洞的"我来分析一下"敷衍了事
- 上限 800：防止冗长的思考占用 token 配额而压缩实际提取空间

### 3.3 Schema 验证 / 数据质量（`_evaluate_quality`，权重 0.2）

```
质量分 = required字段覆盖率 × 0.2 + 关键词项格式合规率 × 0.1
```

1. **Required 字段检查**：Schema 中标记为 required 的字段是否都存在且非 null
2. **关键词项验证**（针对 `keywords` 数组中的每一项）：
   - 必须是长度为 3 的数组 `[说明, 关键词, 置信度]`
   - 关键词长度 ∈ [1, 4] 个字符
   - 置信度为 [0, 1] 之间的数字
   - 合规项比例越高，分数越高
3. **数量上限**：若关键词数 > `max_items`(15)，扣 0.1 分

### 3.4 准确率 / F1 Score（`_compute_f1`，权重 0.5）

```
F1 = 2 × Precision × Recall / (Precision + Recall)
最终准确率分 = F1 × 0.5
```

- 将预测关键词和 Ground Truth 关键词分别转为集合
- 计算交集（True Positive）
- 当无 Ground Truth 时（纯推理模式），如果输出有效内容则给予 0.2 的鼓励分

### 3.5 幻觉惩罚（`_check_hallucination`）

```
惩罚 = min(幻觉词数 × 0.1, 0.3)
```

- 从 Prompt 中正则提取原文文本
- 检查每个预测关键词是否出现在原文中
- 每个幻觉词扣 0.1 分
- 设置上限 0.3，防止单条样本惩罚过重导致梯度不稳定

## 4. Reward Hacking 分析

### 4.1 训练日志中的实际观察

GRPO 训练结束时（924 steps，约 4.5 小时）：

```
reward: 0.9375
frac_reward_zero_std: 0.75
kl: 0.00044703
completions/mean_length: 998.9
```

**Reward 变化曲线：**

![GRPO Reward](./assets/grpo_v2-20260105-090134/images/train_reward.png)

**frac_reward_zero_std 变化曲线：**

![frac_reward_zero_std](./assets/grpo_v2-20260105-090134/images/train_frac_reward_zero_std.png)

**关键信号：`frac_reward_zero_std = 0.75`**

含义：75% 的训练 batch 中，同一 prompt 的所有生成结果获得了完全相同的奖励（方差为零）。这强烈暗示模型已学会一种"固定策略"——对于大多数输入，无论如何采样，输出高度一致。

结合 `reward = 0.9375`（接近满分）和 `kl = 0.00045`（极低的 KL 散度），说明模型在保持接近参考策略的情况下就能稳定获得高奖励，可能已达到奖励函数的"天花板"。

### 4.2 潜在 Hacking 点分析

#### Hacking 点 1：思考部分模板化

**风险**：模型学会固定的"第一步...第二步...第三步..."格式化模板，每次只替换具体关键词，但推理过程本身是"填模板"而非真正分析。

**证据**：`completions/mean_length = 998.9` 非常稳定，暗示输出长度高度一致。

**当前防御**：
- 思考权重仅 10%，模板化思考的收益上限低
- 思考内容检测分析性关键词

**改进建议**：引入思考多样性检测（同一 batch 内不同生成的思考内容相似度不应过高）

#### Hacking 点 2：数量博弈

**风险**：输出尽可能多的关键词（接近 max_items=15）以提升 Recall，即使部分关键词边界模糊。

**当前防御**：
- 超出 15 个会被扣 0.1 分
- 幻觉惩罚机制约束了"瞎猜"行为
- Precision 和 Recall 在 F1 中平衡

**改进建议**：引入数量惩罚的梯度（如 10-15 个轻微扣分，>15 大幅扣分）

#### Hacking 点 3：保守策略

**风险**：模型只输出最安全、最明显的短词（如"好""快""大"），以确保不触发幻觉惩罚和长度违规。

**证据**：`reward_std = 0.125` 较低，说明大多数生成获得相似的高分。

**当前防御**：
- F1 中 Recall 要求覆盖 Ground Truth，遏制过度保守
- 50% 的准确率权重确保"少而全错"不如"多而大部分对"

**改进建议**：对关键词覆盖度设立最低阈值

#### Hacking 点 4：JSON 格式过拟合

**风险**：模型优先确保 JSON 格式完美（可稳拿 format_weight + quality_weight = 0.4），然后用安全内容填充。

**当前防御**：
- 0.4 的格式/质量分只是"门票"，50% 的 F1 分数才能拉开差距
- 有效 F1 为 0 的情况下，最高只能拿 0.5 分

**改进建议**：考虑将格式/质量分设为门槛（不满足则 F1 计为 0），而非加法

### 4.3 已采取的防御措施汇总

| 防御机制 | 对抗的 Hacking 行为 |
|----------|---------------------|
| `max_items = 15` | 防止无限制输出关键词刷 Recall |
| `max_keyword_length = 4` | 防止输出长短语冒充关键词 |
| `hallucination_check` | 防止编造不在原文中的关键词 |
| `max_hallucination_penalty = 0.3` | 惩罚有上限，防止梯度崩溃 |
| `thinking length [50, 800]` | 防止空洞思考或无限冗长 |
| `F1 权重 50%` | 确保核心目标占主导，格式不能"白嫖"高分 |

### 4.4 后续改进方向

1. **引入多样性奖励**：同一 prompt 的不同采样应产生略有差异但都合理的输出，惩罚过度确定性
2. **动态权重调整**：训练前期格式权重高（先学会结构），后期逐步提升 F1 权重
3. **对抗性验证**：定期用人工构造的 edge case 测试奖励函数是否被利用
4. **更细粒度的 F1**：区分"完全遗漏"和"部分遗漏"，对高频词给予更高的 Recall 权重

## 5. 消融实验思路

以下实验方案用于验证各维度权重的合理性：

| 实验编号 | 配置变更 | 预期效果 | 验证假设 |
|----------|----------|----------|----------|
| A1 | F1 权重 80%, 格式+Schema 10% | F1 提升但格式错误增加 | F1 是最重要的信号 |
| A2 | 思考权重 30% | 推理更长但关键词质量下降 | 过高的思考权重有害 |
| A3 | 去掉幻觉惩罚 | 关键词数增加，但幻觉率上升 | 幻觉惩罚是必要的 |
| A4 | 幻觉惩罚上限 0.1 → 0.5 | 模型更保守，Recall 下降 | 过强惩罚导致保守策略 |
| A5 | 所有权重均匀 (0.25×4) | 各维度均衡但无突出优势 | 不等权设计的必要性 |

## 6. 与 ms-swift 集成

奖励函数通过 ms-swift 的 ORM 插件机制注册：

```python
# 在 reward_builder.py 末尾
if HAS_SWIFT:
    orms['schema_based_reward'] = SchemaBasedReward
```

GRPO 训练脚本中通过以下参数引用：

```bash
--external_plugins ./reward_builder.py
--reward_funcs schema_based_reward
```

ms-swift 在每个训练 step 中会：
1. 为每个 prompt 生成 `num_generations` 个 completion
2. 调用 `SchemaBasedReward.__call__(completions, solution, prompts=prompts)`
3. 使用返回的奖励分数计算 GRPO 优势估计
4. 更新策略梯度
